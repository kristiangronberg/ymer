# ymer-marketplace

The `ymer` Claude Code plugin marketplace. See `README.md` for what using the plugins requires and the install commands.

## Conventions

- Domain terms for this repo live in the root `glossary.md`: documents use a term and point at its home, never redefine it. A plugin that ships its own glossary file has one pointer entry in the root, and its skills read that file rather than this one — a front receives a plugin's own files and no repo-level file.
- Edit a plugin in place and it is live in every session that has the marketplace added by path — no update step, no version bump. Keep the working tree runnable.
- Run `claude plugin validate .` and `claude plugin validate plugins/<plugin>` after touching any manifest.
- Skill prose is intent-first: state what is protected and why, and let the executor derive edge handling — enumeration ages worse than intent. Reserve hard MUST wording for spots where failure is silent and expensive.
- The personal-layer principle: nothing personal to the maintainer may be necessary to run the plugins — not directly as a requirement, and not indirectly as personal config papering over friction other users would hit. Anything a plugin needs beyond what its prose states and the user brings is a defect. A skill never writes user state into the plugin tree: an install runs from a copy of it, and a write into the repository ships to every user of the marketplace — user state belongs in the user's own stores: the Ymer Node, ymer, or the state folder. The standing check is the hermetic probe, `scripts/hermetic-probe`: an isolated `CLAUDE_CONFIG_DIR` with only this marketplace installed, pointed at a scratch Ymer Node whose notebook starts empty, and every headless run given that node as its one MCP server by `--strict-mcp-config` — a logged-in config dir carries the login's own claude.ai connectors, ymer among them, which no scrub removes — so the skills find no ymer. With no state folder named, `/ymer:setup` must create the skeletons, fail its state-folder check with the fix, and report the coordinator by reach, and `/ymer:kaizen-summary` must stop at its guard naming `/ymer:setup`; with a scratch folder that is not a git work tree named as the state folder, setup must report it tracked by `topics_history`, and summary must drain into it — the file in the folder and a matching `topics_history` row. The skills must load and resolve their references, and every skill must stop with setup guidance where the node is missing. Run bare it runs the static and eval stages, the check for every change; `scripts/hermetic-probe live` adds the scratch node and the install path, for a change to setup's skeletons, the install lines or a store-writing skill; `scripts/hermetic-probe-test` tests the probe itself with no model. A live check reads a skill's report for the facts its lines carry, through the live stage's `report_lines`, never for its form: the model dresses a right report differently from run to run, and a check on the dress reads red on a right report.
- Eval cases live in one `evals/` at the root, one `case.yaml` per skill, run by the probe's eval stage through `claude plugin eval`. What a case author needs to know: a run loads nothing personal — your own MCP servers never load, so a case sees no node and asserts the skill's stop; a case must sit under the containment root, the directory the runner is pointed at, and a root-target run sweeps every `evals/<case>/` beneath it, so no plugin carries an `evals/` of its own; `tool_used: Skill` is flaky for a slash-invoked skill — assert that a skill fired with a `regex` over `trace` for the init event's plugin and slash command and for the skill's announce line; and a `regex` over `trace` sees the raw stream-json with its quotes unescaped — `"mcp_servers":\[\]` matches, `\"mcp_servers\"` does not. A skill that carries a guard carries a case: the case asserts the guard's stop, and each case arrives with its guard.
