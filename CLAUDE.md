# ymer-marketplace

The `ymer` Claude Code plugin marketplace. See `README.md` for what using the plugins requires and the install commands.

## Conventions

- Domain terms for this repo live in the root `glossary.md`: documents use a term and point at its home, never redefine it. A plugin that ships its own glossary file has one pointer entry in the root, and its skills read that file rather than this one — a front receives a plugin's own files and no repo-level file.
- Edit a plugin in place and every new session that has the marketplace added by path runs the edit — no update step, no version bump. A running session keeps the skill bodies it loaded until `/reload-plugins`. Keep the working tree runnable.
- The plugins describe only the present. Before 1.0 a release carries no migration for state an earlier release left behind: it states how things work now, and a user re-runs `/ymer:setup` after upgrading. Handling deprecated state is a question for 1.x.
- Run `claude plugin validate .` and `claude plugin validate plugins/<plugin>` after touching any manifest.
- Skill prose is intent-first: state what is protected and why, and let the executor derive edge handling — enumeration ages worse than intent. Reserve hard MUST wording for spots where failure is silent and expensive.
- A skill never writes user state into the plugin tree: an install runs from a copy of it, and a write into the repository ships to every front that installs from it. User state belongs in the user's own stores: the Ymer Node, ymer, or the state folder.
- The plugins are maintained, not developed: the Ymer product page's measuring rule decides what they take. `scripts/hermetic-probe` (static, eval, live) and the eval cases under `evals/` stay available and gate no change. They are not developed further, and one a change breaks is retired, partly or whole, rather than reworked.
- Eval cases live in one `evals/` at the root, one `case.yaml` per skill, run by the probe's eval stage through `claude plugin eval`. What a case author needs to know: a run loads nothing personal — your own MCP servers never load, so a case sees no node and asserts the skill's stop; a case must sit under the containment root, the directory the runner is pointed at, and a root-target run sweeps every `evals/<case>/` beneath it, so no plugin carries an `evals/` of its own; `tool_used: Skill` is flaky for a slash-invoked skill — assert that a skill fired with a `regex` over `trace` for the init event's plugin and slash command and for the skill's announce line; and a `regex` over `trace` sees the raw stream-json with its quotes unescaped — `"mcp_servers":\[\]` matches, `\"mcp_servers\"` does not. That stream carries the model's output and the tool results, never the body of a slash-invoked skill, so a `trace` pattern copied from a skill's text matches only where the model prints it or a tool result carries it, as a `Read` of the skill file would.
